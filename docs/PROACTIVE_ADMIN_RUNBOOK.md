# Proactive watch — platform admin runbook (keys, connectors, testing)

Created 2026-11-02 under the owner's instruction: "build thos framework and workflows and this
intire plan, once all are done, then ill input the keys and we can test them at the last."
It supersedes nothing; it is linked from [PROACTIVE_MULTI_HAZARD_PLAN.md](PROACTIVE_MULTI_HAZARD_PLAN.md)
and [PROACTIVE_IMPLEMENTATION_CONTRACT.md](PROACTIVE_IMPLEMENTATION_CONTRACT.md).

Everything is off by default. Nothing here sends a warning, dispatches anyone, or contacts an
authority. Keys you enter only let AEGIS **read** public data and, optionally, ask TypeSafe/Jev
for typed judgments over cited records.

## 1. One-time setup (Windows laptop)

1. Create the master key that encrypts stored secrets (kept outside the repo):
   `powershell -File .\scripts\new-connector-key.ps1` — copy the printed value into your shell as
   `$env:AEGIS_CONNECTOR_KEY` for the session that starts Compose. Losing it means re-entering the
   keys; it is never stored in the database.
2. Provision the review-only local IdP (see [LOCAL_IDP_REVIEW.md](LOCAL_IDP_REVIEW.md)) if you want
   real sign-in. It now includes an `exercise-admin` user holding the `platform_admin` role
   (password generated by `scripts/prepare-local-idp.ps1 -GenerateLocalSecrets`, TOTP required).
   Roles come only from the signed token; the browser cannot grant itself admin.
3. Start with the proactive overlay: `.\scripts\start-windows.ps1 -Proactive`.

## 2. Entering and testing keys

Sign in as `exercise-admin`, open **Connectors** (`/admin/connectors`).

| Connector | What to enter | Where to get it | Test performs |
|---|---|---|---|
| Open-Meteo | nothing (optional settings) | none | one 1-day forecast request |
| NASA FIRMS | `map_key` | https://firms.modaps.eosdis.nasa.gov/api/ (free) | tiny area request |
| NASA LHASA | nothing | none | status request |
| Copernicus Data Space | `client_id`, `client_secret` | free CDSE account, OAuth client | token request only |
| IMD warnings | tick `terms_accepted` only after IMD terms are confirmed | IMD | blocked until ticked |
| TypeSafe / Jev | `api_key`, model, monthly input-token budget | TypeSafe account (paid) | list-models request |
| CAP hand-over | none | — | validates the exporter |
| Authority notification | cannot be enabled | — | always refused |

Per connector: fill fields → **Save** (secrets are write-only; afterwards you see only "set" and a
short fingerprint) → **Test** → check status, latency and message → toggle **Enabled**.
Every save, clear, enable and test is audited (no secret values). If Save reports a version
conflict, someone else changed it: reload and retry.

## 3. Using it

- **Hazard Watch** (`/watch`): *Refresh* pulls from enabled connectors only; triggers appear as
  watch/candidate with cited evidence. Select one for the Live | Predicted panel.
- *Start bounded run* walks five steps (gather evidence → simulate variants → judge → draft CAP →
  hand to human). Without a Jev key the judgments come from a labelled deterministic test double.
  The result is advisory: `recommended`, `needs review` or `blocked`.
- The CAP file is an **Exercise** draft for a human to give to the authority's own SACHET/NavIC
  process. AEGIS never transmits it.

## 4. Safe-testing checklist (do these in order)

1. Open-Meteo test OK → Refresh → evidence and triggers appear.
2. FIRMS test OK → Refresh → fire evidence appears (may be zero detections; that is valid).
3. LHASA test (may fail: NASA's server is best-effort; failure must not break Refresh).
4. Jev test OK → start a run → provider shows `typesafe_jev`, probabilities visible.
5. Disable Jev → start a run → provider shows `test_double`.
6. Clear a secret → connector shows "not set" and its test fails cleanly.
7. Try to enable *Authority notification* → refused.
8. Confirm `/watch` still works signed out (read-only) and `/admin/connectors` does not.
9. Engage the kill switch (section 5) → Refresh and *Start bounded run* are refused with
   `proactive_paused`, `/watch` shows the paused banner, an existing run still opens and can be
   cancelled → resume with a reason.
10. Sign in as an operator of a second agency → a run started by the first agency is not listed
    and its URL returns "not found".

## 5. Kill switch

Requires migration `013_proactive_run_agency.sql` (applied by the Compose `migrate` service).

- **Where:** the *Proactive kill switch* panel at the top of `/admin/connectors` (platform_admin
  only). Any signed-in operator can read the state (`GET /api/proactive/pause`); only
  platform_admin can change it (`PUT`, same-origin checked by the BFF).
- **Effect while paused:** run start, run advance and watch refresh return HTTP 409 with code
  `proactive_paused`, for every agency. Reads (`/watch`, history, run detail, CAP download),
  cancellation and existing drafts are untouched. Hazard Watch shows a "paused" banner.
- **Audit:** every change needs a 10–500 character reason and writes one append-only
  `proactive_pause_audit` row (paused flag, reason, actor = verified token subject, time). The
  panel shows the last 20 changes.
- **Fail closed:** if the switch cannot be read (for example 013 not applied), the blocked
  routes return 503 instead of assuming "not paused"; the watch shows no banner (`paused: null`).

## 6. Agency scope of runs

- A run records the creating operator's verified `aegis_agency_id` in `proactive_runs.agency_id`.
  The agency is never taken from the browser or request body (extra fields are rejected).
- Get, list, advance, cancel and CAP download only see runs of the operator's own agency. A run in
  another agency returns **404 `run_not_found`**, not 403, so its existence does not leak.
- Runs created before migration 013 have `agency_id` NULL and are **invisible to every scoped
  route** (fail closed). They are not back-filled or deleted; their audit rows stay in the DB.
  If one must be recovered, an owner-approved one-off `UPDATE` that sets the correct agency is
  the only path; do not guess.
- Evidence and triggers remain shared reference data across agencies (they hold no case data).

## 7. Scheduled watch loop (A1, autonomy L3: prepare and route, never act)

Requires migration `014_proactive_scheduler.sql` (applied by the Compose `migrate` service) and
the proactive overlay. Default **off**; base Compose and `compose.proactive.yaml` never enable it.

- **Where it runs:** one daemon thread inside the API process, started by the app lifespan only
  when `AEGIS_PROACTIVE=1`, `AEGIS_PROACTIVE_SCHEDULER=1` and `AEGIS_PROACTIVE_SCHEDULER_AGENCY_ID`
  is a UUID. A separate one-shot-loop service was not chosen: it would need its own image, DB
  credentials and lifecycle under the single-instance rule, while the in-process loop reuses the
  API's store, connector allowlist, kill switch and run code unchanged. Multi-worker safety comes
  from the database, not from the process layout (see "Concurrency").
- **Refusal:** if the agency is unset or not a UUID the loop does not start and logs one fixed
  reason (`scheduler_agency_missing`, `scheduler_agency_invalid`, `scheduler_requires_proactive`).
  The agency comes only from this trusted environment variable, never from a request.
- **Interval:** `AEGIS_PROACTIVE_SCHEDULER_INTERVAL` seconds, default 1800, minimum 300 (lower or
  invalid values are raised to 300 / reset to 1800). The first tick runs 60 s after API start.
- **Each tick:** take the advisory lock → if the kill switch is engaged record `skipped_paused`
  and stop (an unreadable switch records `failed` / `pause_unreadable`: fail closed) → refresh
  evidence → run the sentinel (section 8) → for each new `candidate` trigger with no open run for
  the same area/hazard, start a run as `system:scheduler` and advance only `gather_evidence`,
  `simulate_variants`, `judge`, `draft_cap`. The run stays `running` with next step
  `hand_to_human`. At most 5 runs per tick (`run_cap_reached`). The pause is re-checked before
  every step (`paused_mid_tick`).
- **Judge cost:** the `judge` step uses the Typesafe Jev connector exactly like a manual run. If Jev
  is enabled, each prepared run spends from its monthly token budget; with Jev disabled the
  deterministic test double answers. Keep Jev disabled if automatic spend is not wanted.
- **Concurrency:** each tick holds `pg_try_advisory_lock(7311402014)` on a dedicated connection;
  a second worker or replica records `skipped_locked`. Scheduler runs carry
  `dedupe_key = sha256(agency, trigger_id, config_version, cited evidence sha256s)`; the partial
  unique index `proactive_runs_dedupe_idx` makes a second run for the same evaluation impossible.
- **Never acts:** `system:` subjects are rejected as OIDC token subjects (401), as proposal maker
  or checker (`governance.submit/review`) and for the `hand_to_human` step
  (`system_actor_cannot_hand_off`). Nothing is submitted, approved, sent or notified. A signed-in
  `incident_operator` opens the trigger on Hazard Watch, the panel resumes the open run ("Prepared
  by the scheduler") and that person takes the hand-off.
- **Tick log:** one append-only `proactive_scheduler_ticks` row per tick: outcome (`completed`,
  `skipped_paused`, `skipped_locked`, `failed`), runs started, flags recorded and fixed error codes
  only. `GET /v1/proactive/scheduler` (BFF `GET /api/proactive/scheduler`; incident_operator,
  checker, auditor, platform_admin) returns on/off, interval, last and next tick and the last 10
  ticks of the caller's own agency (platform_admin: all agencies; agency ids are never echoed).
  Hazard Watch shows a "Scheduler: on/off, last tick, next tick" strip. `next_tick_at` and
  `running` describe the API worker that answered.

**Enable on the running stack** (one AEGIS operation at a time; no volume reset):

```powershell
scripts/check-local-runtime.ps1 -RequireRunning
docker compose --project-name ai-project-aegis run --rm migrate   # applies 014 idempotently
$env:AEGIS_PROACTIVE_SCHEDULER_AGENCY_ID = "<agency uuid of the operators who will review>"
$env:AEGIS_PROACTIVE_SCHEDULER_INTERVAL = "300"                  # optional, for verification
powershell -ExecutionPolicy Bypass -File scripts/start-windows.ps1 -NoBuild -ProactiveScheduler
```

**Verify:** `docker compose logs api` has no `scheduler_agency_*` line; after ~60 s
`/api/proactive/scheduler` shows a `completed` (or `skipped_paused`) tick; engage the kill switch
and confirm the next tick is `skipped_paused`; a candidate trigger yields one run whose next step
is `hand_to_human`; a second tick on unchanged evidence starts no second run;
`python -m app.migration_audit` reports `ready`. **Disable:** restart with `-Proactive` (without
`-ProactiveScheduler`) or engage the kill switch.

## 8. Evidence-change sentinel (A2)

- Runs after every evidence refresh: the manual `POST /v1/proactive/watch/refresh` (for the
  caller's agency) and each scheduler tick (for the scheduler agency).
- For every open run (`status = running`) it compares the run's trigger with the newly evaluated
  trigger for the same area/hazard and appends at most one flag: `strengthened` (score up),
  `weakened` (score or state down), `contradicted` (the trigger would no longer fire) or `stale`
  (no new evaluation and the newest cited evidence is older than 24 h). Each flag cites up to 20
  evidence ids and a timestamp. An identical consecutive flag is not repeated.
- Flags are appended through the row-locked run update with actor `system:sentinel`, so each one
  has a `sentinel_flag` audit row. The run state keeps the newest 50; the audit keeps all.
- It never edits drafts, variants, judgments or CAP content, never advances or cancels a run and
  never sends anything. A sentinel failure never fails the refresh (`sentinel_failed` code). The
  run panel lists the flags; a flag is an observation for the reviewer, not a forecast.

## 9. Impact-based triggers and the exposure layer (A3)

Requires migration `015_exposure.sql` (Compose init `019-exposure.sql`, `migrate` chain
`-f /exposure.sql`) and, for the demo data, the synthetic seed `db/seed_exposure.sql` (init
`020-exposure-seed.sql`, `seed` chain `-f /seed-exposure.sql`). Both are additive and idempotent.

- **What changes:** after each refresh the hazard state of every trigger is combined with the
  exposure counted inside a fixed circular exercise footprint (`app/impact.py`, versioned rules
  `app/fixtures/impact_triggers.v2.json`, `aegis.impact-triggers.v2`). For `candidate`, then
  `watch`: the hazard state must be at least the rule's `min_hazard_state` **and** one of
  `people_exposed`, `critical_facilities` (hospital, school, shelter) or `road_segments` must reach
  its threshold (inclusive). Otherwise the impact state is `clear`. Deterministic code, no model.
- **Fallback:** if `exposure_features` is empty or unreadable (015 not applied) the hazard state is
  kept and the trigger is labelled **hazard-only** (`exposure_layer_empty` / `exposure_unavailable`).
  v1 hazard thresholds (`hazard_triggers.v1.json`) are unchanged; `GET /v1/proactive/triggers/config`
  still returns v1, and `GET /v1/proactive/triggers/impact-config` returns the v2 rules and feed thresholds.
- **Citations:** the trigger rationale carries `impact` with the counts, the cited exposure feature
  ids (up to 50), `data_basis` (`synthetic`, `licensed`, `mixed`, `none`) and the label shown on
  Hazard Watch cards and the run panel, e.g. **impact-based (synthetic exposure)**. The run's
  `gather_evidence` step copies this block into the run state and its audit row; the Exercise CAP
  area description and instruction use fixed templates with the integer counts and basis and add
  `aegis.exposure_feature_id` parameters. Counts are rehearsal inputs, not damage, casualty or
  inundation estimates.
- **Scheduler:** the dedupe key now also includes the impact config version/status and the cited
  exposure feature ids, so a new impact config or new exposure data counts as a new evaluation.
- **Synthetic seed:** 13 fictional features around the Hyderabad pilot grid (central point and
  Musi reach have exposure, the downstream point a little, the other grid points none). All rows
  are `synthetic = true`; names, positions and population counts are invented.
- **Real data (owner action, offline importer, not run by the assistant):** place extracts on the
  laptop, then inside the API container or `services/api/.venv`:

  ```powershell
  # OSM GeoJSON extract (ODbL 1.0; attribution "(c) OpenStreetMap contributors")
  python -m app.exposure_import osm --file C:\data\hyderabad-osm.geojson --batch osm-2026-11 --bbox 78.2,17.2,78.7,17.6 --dry-run
  python -m app.exposure_import osm --file C:\data\hyderabad-osm.geojson --batch osm-2026-11 --bbox 78.2,17.2,78.7,17.6
  # WorldPop grid (CC BY 4.0). Convert the GeoTIFF first; the importer has no raster dependency:
  #   gdal_translate -of XYZ ind_ppp_2020_constrained.tif hyd.xyz
  python -m app.exposure_import worldpop --file C:\data\hyd.xyz --batch worldpop-2020 --cell-deg 0.0008333 --bbox 78.2,17.2,78.7,17.6
  ```

  Hospitals/clinics, schools/colleges, shelters/assembly points and motorway–tertiary roads are
  kept; everything else is skipped and reported. Each row records source, source ref, licence,
  attribution, `synthetic = false`, a provenance sha256 and the batch; re-imports are idempotent.
  `DATABASE_URL` must point at the local stack. Keep the extracts local and do not redistribute
  them; show the attribution wherever counts are presented. Real and synthetic rows can coexist
  (`data_basis = mixed`); to rehearse with real data only, the owner may delete the
  `synthetic-seed-v1` batch rows by hand — never reset the volume.

## 10. GDACS and Google Flood Forecasting connectors (A4)

Both are default **disabled**, use the same allowlisted `bounded_request` (HTTPS only, fixed host,
no redirects, no proxy, size and time caps) and parse JSON only (no XML parser is added).

- **GDACS** (`gdacs`, host `www.gdacs.org`): public event list
  `/gdacsapi/api/events/geteventlist/SEARCH` for FL/TC/EQ/WF/DR/VO over the last 1–7 days (`days`
  setting); events outside the India bounding box are dropped. Alert levels map to evidence values
  green 1, orange 2, red 3; `aegis.feed-triggers.v1` treats orange as `watch` and red as `candidate`
  (synthetic mapping). No key. **Terms of use: to confirm by owner** before enabling
  (https://www.gdacs.org/About/termofuse.aspx); attribution "GDACS (UN / European Commission JRC)".
- **Google Flood Forecasting** (`google_flood_forecasting`, host `floodforecasting.googleapis.com`):
  `POST /v1/floodStatus:searchLatestFloodStatusByArea` with `regionCode = IN`; gauges within 150 km
  of the pilot grid are kept. Severity maps NO_FLOODING 0, ABOVE_NORMAL 1, SEVERE 2, EXTREME 3;
  `watch` from 1, `candidate` from 2. **Waitlist approval pending:** the connector cannot be enabled
  until a platform_admin saves an API key (`required_secret_missing:api_key`). The key is stored
  encrypted, sent only in the `X-Goog-Api-Key` header (never in a URL), and never logged or
  returned — only its 8-hex fingerprint is shown. Data CC BY 4.0, attribute Google Flood Forecasting.
- **Testing:** the admin page lists both connectors from the registry. *Test* sends one bounded
  request (GDACS: 1-day window; Google: one status search) and keeps only status and latency.
  Unit tests use hand-authored offline fixtures (`services/api/tests/fixtures/`), not live captures.
- Feed events are third-party references, not AEGIS assessments; they pass through the same impact
  rules (25 km GDACS footprint, 8 km gauge footprint) and never create cases or warnings.

## 11. What it will not do

No scraping, social media or webcams. No broadcast. No automatic case, proposal, approval or
task. No accuracy claim: thresholds are synthetic rehearsal values until the registered
evaluation (`python -m app.proactive_replay`) has real reviewed labels.
